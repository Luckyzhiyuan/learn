## 1. 知识四层架构（补齐 Spec 5.1 的设计理念）

**核心纠正**：NL2SQL 的第一上下文**不是向量库，而是结构化语义层（L1）**。表/字段/指标是**事实**，应走 SQL 精确查询（Schema Linking）；文档是**解释**，才走向量模糊召回。把文档塞给 NL2SQL 当主上下文，是引入噪声、拖慢响应、降低准确率的头号错误。

```text
L4 运行时上下文（不入库向量，仅会话内短暂保留，Redis TTL 1h）
    对话历史、用户偏好、临时澄清
    ↑
L3 经验知识层（向量 + 结构化标签）          ← few-shot 样例来源
    SQL 样例、改写案例、历史问答对(高赞)、事故复盘、取数套路 FAQ
    ↑
L2 文档知识层（向量为主）                    ← 口径补充上下文
    口径说明、建模规范、Wiki/Word、数据字典、变更说明、故障手册
    ↑
L1 结构化事实层（MySQL，不走向量）           ← NL2SQL 主上下文
    meta_*(元数据)、semantic_*(语义层)、血缘、quality_*、指标
```

| 层 | 存储 | 检索 | 是否被 NL2SQL 直接使用 | 说明 |
|----|------|------|----------------------|------|
| L1 | MySQL | SQL 精确查询 / join | ✅ **主上下文** | 权威、可控、可解释 |
| L2 | MySQL(chunk) + ES | BM25 + kNN | ✅ 补充口径 | 必须带溯源 |
| L3 | MySQL(chunk) + ES | 混合 + 标签过滤 | ✅ few-shot 来源 | 采纳后沉淀，正向飞轮 |
| L4 | Redis | 直取 | ✅ 多轮澄清 | TTL 短，不落库 |

> 一句话：**能用 SQL 查到的，绝不放进向量库**。向量库只放"无法结构化"的文本。

**对 Spec 5.3 RAG 流程的修正**：原流程把"知识库"笼统当作向量检索，现改为**意图分流**：

```text
用户问句 → 意图识别(规则+千问轻量分类)
  ├─ 取数类 → L1 Schema Linking(SQL查meta/semantic) + L3 few-shot召回
  ├─ 口径类 → L2/L3 混合检索
  └─ 排障类 → L2(INCIDENT) + L1(质量/血缘)
→ 权限前置过滤 → 混合召回 → RRF融合 → Top-K→ 拼装上下文(带溯源) → LLM生成
```

## 2. 知识分类体系升级（补齐 Spec 5.2 的 kb_type）

现有 Spec 用 `glossary/alias/sql_example/mapping/rule`，粒度不够、易歧义。升级为规范枚举，**keyword 存值，兼容旧值迁移**：

### 2.1 kb_type 枚举

| 码 | 类型 | 内容示例 | 来源 | 向量化 | 优先级 |
|----|------|---------|------|--------|--------|
| `METRIC` | 指标口径 | "间夜量=SUM(入住天数)，排除取消" | 人工/文档抽取 | ✅ | P0 |
| `SEMANTIC` | 表/字段业务含义 | "validdays=里程有效期天数" | F0 自举+校正 | ⚠️ 已在 L1，只存索引指针 | P0 |
| `TERM` | 业务术语/黑话 | "ADR/OCC/RevPAR/间夜" | 人工/术语表 | ✅ | P0 |
| `FAQ` | 取数 FAQ | "怎么查上月各酒店GMV？" | 沉淀 | ✅ | P1 |
| `SQLCASE` | SQL 样例/改写案例 | 优化前后 SQL+说明 | F3 沉淀 | ✅ | P1 |
| `RULE` | 规范与规则 | SQL MUST DO/MUST NOT、质量规则 | 配置同步 | ✅ | P1 |
| `INCIDENT` | 事故复盘 | "dwd 层延迟 3h，根因…" | 人工 | ✅ | P2 |
| `GLOSSARY` | 主题域/资产说明 | 域划分、责任人、SLA | 人工 | ✅ | P2 |

> **SEMANTIC 特殊处理**（重要）：字段语义已在 `semantic_column`(L1)，**不重复切分入库**，向量库只建一条轻量索引指针（指向 col_id），避免"两处维护、必然不一致"。

### 2.2 主题域（domain）

按分层 `dim/dwd/ads/etl/tmp/rpt` 作为层级标签，另加业务域标签（酒店/里程/订单/会员…）。检索时先按域收敛、再语义召回。`kb_document` 增加 `domain` 字段。

## 4. 混合检索架构（补齐 Spec 5.3 的重排细节）

### 4.1 检索流水线

```text
用户问句
  → 意图识别(规则+千问轻量分类)
  → 权限前置过滤(按 user.role 过滤 acl_level，检索阶段执行)   ← 关键，非召回后
  → 混合召回: ES BM25(ik中文分词) + ES kNN(dense_vector) + 结构化过滤(domain/layer/kb_type/verified/status)
  → 融合重排: RRF 倒数排名融合(或可选 rerank 模型)
  → Top-K(K=5) 拼装上下文，每条附 [doc_id, chunk_id, version, 来源链接]
  → LLM 生成，强制引用标注 [1][2]
  → 输出 + 溯源面板(可点开原文/可反馈/可一键纠错)
```

### 4.2 硬性规则

- **无溯源不输出**：答案中每个事实性断言必须带引用；无法引用时回答"知识库未覆盖，建议咨询 owner"。
- **Top-K 上限 5**：上下文越长越易漂移，宁缺毋滥。
- **权限过滤在检索层**：分片写入时打 `acl_level`，检索按用户角色过滤，**不在召回后处理**（召回后再过滤，被过滤内容已进 LLM 上下文，可能出域）。
- **缓存**：问答对缓存(Redis，TTL 1h)，降千问成本。

### 4.3 切分策略（显著影响召回质量）

| 知识类型 | 切分方式 | chunk 大小 |
|---------|---------|-----------|
| METRIC / TERM / SEMANTIC | **不切分**，一条=一个 chunk | 100-300 字 |
| 文档(md/docx) | 按**标题层级**切(H2/H3为界)，不足再按段落合并 | 300-600字 + 15%重叠 |
| SQLCASE | 一条=一个 chunk(含SQL+说明) | — |
| **标题路径前缀(必做)** | 每个 chunk 文本前拼 `【域>文档>章节】` | — |

> 标题路径前缀让 ES 关键词命中"章节归属"，成本几乎为零但能显著提升召回准确率。

### 4.4 Embedding 模型与 ACL 路由

| 用途 | 主选 | 降级/不出域备选 | 注意 |
|------|------|----------------|------|
| 中文知识向量化 | 千问 `text-embedding-v3/v4`(1024维) | 本地 Ollama `bge-large-zh`(1024维) | **维度必须一致**，换模型=全量重建索引 |
| 出域判断 | ⚠️ 调千问 embedding=知识文本出域 | 涉密知识走本地模型 | 见 §6 |

## 5. 防腐烂生命周期机制（本设计核心，Spec 5.6 的完整化）

**核心判断**：知识库最大的敌人不是"内容少"，是"腐烂"。三个月没人维护的口径文档，比没有文档更危险——它会让 AI 自信给出错误答案。**鲜度机制和 owner 机制必须与入库功能同期做**。

```text
采集(Ingest) → 结构化(Structure) → 校验(Verify) → 发布(Publish)
→ 消费(Retrieve) → 反馈(Feedback) → 鲜度衰减(Decay) → 归档/失效(Archive)
```

| 环节 | 机制 | 落地 |
|------|------|------|
| **Owner** | 每条知识必须有 owner | 表知识=表负责人；指标=提出人。**无 owner 不允许发布**（接口层强制校验） |
| **校验** | LLM 生成内容一律 `verified=false`，人工确认后才 true | 与 F0.3 校正界面共用 |
| **版本** | `version` + `superseded_by`，历史保留可回溯 | 口径变更可 diff |
| **鲜度** | `last_verified_at`；超 **90 天**未复核 → 转 `stale`，检索降权(不删除) | 看板暴露"逾期知识数" |
| **失效触发** | **元数据变更自动触发**：字段删除/改类型 → 关联 METRIC/SEMANTIC 自动转 stale + 通知 owner | 复用 F1.5 快照 diff，低成本高价值联动 |
| **引用计数** | `cited_count`(被问答引用次数) | 高引用+高采纳=优质；零引用=考虑归档 |
| **反馈闭环** | 问答页"有用/无用"→ 无用则降权 + 生成待办给 owner | 对应 PRD 反馈埋点 |

**防腐烂执行载体**：`kb_review_task` 表 + 定期 Celery 任务（`kb_freshness_check`）。元数据变更 → 查关联 → 生成复核待办，这是 §3.6 与 L1 的联动点。

## 6. ACL 分级与出域合规（知识库特有新增风险）

> 原 Spec §4.5 只定义了"元数据出域白名单"，但知识库会引入新风险：**文档内容出域**。一份《酒店定价策略》embedding 时被送到千问 API——这不是元数据，属于业务敏感信息。

### 6.1 知识分级（`acl_level` 字段）

| 级别 | 内容 | 可否送外部 embedding | 可否送外部 LLM |
|------|------|--------------------|---------------|
| `L0_PUBLIC` | 通用数仓概念、SQL 语法、公开规范 | ✅ | ✅ |
| `L1_INTERNAL` | 表/字段注释、指标定义、内部 FAQ | ✅(建议) | ✅ |
| `L2_CONFIDENTIAL` | 具体商户/价格/成本/经营策略 | ❌ **本地 embedding** | ❌ 仅送标题与摘要 |
| `L3_RESTRICTED` | 涉个人信息、合规敏感 | ❌ 不入库向量 | ❌ 禁止调用 |

### 6.2 落地

- 知识入库强制打级别（默认 `L1`，创建者可选升级）。
- Model Router 增加 `embed()` 方法，内部按级别路由：L0/L1 → 千问 embedding；L2 → 本地 Ollama `bge-large-zh`；L3 → 拒绝入库向量，仅存结构化字段。
- `llm_call_log` 扩展 `kb_doc_id`、`acl_level`、`payload_hash`，审计可追溯到具体知识条目。

## 7. 知识来源与采集策略（对齐 Spec 5.9）

| 来源 | 采集方式 | 优先级 | 备注 |
|------|---------|--------|------|
| ① **平台内生(首选)** | `meta_*`/`semantic_*`/`quality_*`/`llm_call_log` 视图化 | P0 | 零人工，永远与真实元数据同步，不腐烂 |
| ② **指标口径注册** | F0.4 人工录入界面 | P0 | 当前最缺，从 0 到 1 |
| ③ **本地文档目录** | 扫描 `D:\dw\docs` 的 .md/.docx/.txt/.pdf | P1 | 建议现在就建，形成沉淀习惯 |
| ④ **建表 SQL 注释** | 解析 `verify.sql` 等 COMMENT | P1 | 与"模式一采集"复用解析器 |
| ⑤ **对话沉淀** | NL2SQL/问答被采纳结果 → 生成 FAQ/SQLCASE | P1 | 飞轮起点，"一键沉淀为知识" |
| ⑥ **外部系统(后续)** | Wiki/Confluence API、Git SQL | P2 | 预留 connector 接口 |

> **冷启动建议**：先只做 ①②⑤。①零成本、②补齐最大缺口、⑤让知识自然增长。③④等在闭环跑通后再接——否则会在"采集一堆没人维护的旧文档"上浪费时间、污染检索质量。

## 8. 评测方法（知识库必须能量化）

| 指标 | 定义 | 目标 | 如何测 |
|------|------|------|--------|
| **检索 Recall@5** | 标准问句的正确答案切片出现在 Top5 的比例 | ≥85% | 50 条评测集(问句+期望doc_id)，跑批自动算 |
| **MRR** | 首个正确结果的排名倒数均值 | ≥0.7 | 同上 |
| **答案有引用率** | 生成答案中带 `[n]` 引用的比例 | **100%**(硬门槛) | 评测集全量跑，任一条无引用即失败 |
| **引用准确率** | 引用指向的切片确实支持该断言 | ≥90% | 人工抽检 20 条 |
| **知识采纳率** | 用户点"有用"比例 | ≥60% | 线上埋点 |
| **鲜度达标率** | 超 90 天未复核知识占比 | ≤20% | `kb_freshness` 看板 |
| **覆盖率** | 有口径知识的核心表占比 | ≥80%(Top-N表) | 关联 `meta_table` 统计 |

> **评测集是前置任务**。50 条问句 + 期望答案切片，在 KB-2 阶段就要建好——否则无法判断"换了切分/换了 embedding 到底是变好还是变坏"。

## 10. 冷启动与三个最容易踩的坑

### 10.1 冷启动策略

当前只有 2 张表、零指标文档。**不要全量灌文档**。先做 **30-50 条高价值知识**跑通"入库→检索→问答→溯源→反馈"闭环，验证有效再规模化。

### 10.2 三个坑

| 坑 | 表现 | 规避 |
|----|------|------|
| **知识重复源** | 字段注释在 semantic_column 和 kb_doc 各存一份，改一处忘另一处 | SEMANTIC 类知识不复制内容，只存指针(见 §2.1) |
| **全量灌文档** | 冷启动把 500 份历史文档全塞进去，检索全是噪声，Recall 反而更低 | 先 50 条高价值知识跑通闭环，评测通过再扩量 |
| **只建不管** | 上线时 100 条，半年后 105 条且一半过期 | §5 生命周期 + §9 KB-4 任务不得裁剪 |

## 13. 与已产出的样例对接

先前《国际酒店主题》样例的知识条目（mapping/alias/glossary）可**按本设计升级归类**：

| 原样例 kb_type | 升级为 | 补充字段 |
|----------------|--------|---------|
| `mapping`(表映射) | `GLOSSARY`(域/资产) + `related_ids` | owner=翟志远、domain=国际酒店、acl_level=L1 |
| `mapping`(platid 字典) | `TERM`(术语) 或保留为 `GLOSSARY` | — |
| `alias`(UV/日期等) | `kb_alias` 原样 | — |
| `glossary`(点位/选表) | `METRIC`/`GLOSSARY` | owner、last_verified_at、source |
| 6 张表字段结构 | 同步进 `semantic_column`(L1) | **不重复入向量，只存指针** |

这样既符合四层架构（表结构走 L1、口径走 L2/L3），又满足防腐烂（每条带 owner/版本/鲜度）与出域合规（L1 级别）。
