# 智能数据开发平台 —— 市场功能全景调研与差距分析

> 定位：补充文档
> 日期：2026-10-12
> 方法：调研 DataWorks、Dataphin、qData、DanaStudio 等行业标杆 + 开源组件，归纳"一站式智能大数据开发治理平台"的功能全景，再对照本项目《智能数仓平台-功能开发文档》《工程Spec-v1.3》找出缺失。
> 结论先行：本项目目前覆盖约 **6 大模块（F1-F6）**，对照市场标杆，**存在 9 块明显缺失**，其中 **4 块属 P0 级**（不补则平台不成体系）。

## 一、市面上智能数据开发平台的功能全景（10 大域）

综合 DataWorks、Dataphin、qData、DanaStudio 等主流产品，一个完整的一站式平台应覆盖以下 **10 大能力域**：

| 域 | 说明 | 标杆能力 |
|----|------|---------|
| **1. 数据集成** | 异构数据源接入、离线/实时同步、全增量 | 50+数据源、实时同步、整库迁移、限速容错 |
| **2. 数据开发** | WebIDE、多语言(SQL/Python)、工作流/Notebook | 跨引擎SQL、Git集成、SQL/Python、Notebook |
| **3. 数据建模** | 数仓分层、维度建模、逆向建模、代码自动化 | 设计即开发、自动化生成代码、逆向建模 |
| **4. 任务调度运维** | 周期/依赖调度、DAG编排、补数、重跑、监控告警、基线 | DAG编排、智能基线、全链路诊断、补数据 |
| **5. 元数据与血缘** | 元数据采集、数据地图、表/字段/列级血缘、影响分析 | 秒级SQL解析、列级血缘、影响分析、口径展示 |
| **6. 数据标准** | 数据标准定义、落标映射、数据字典、术语表 | 标准定义、落标映射、术语表 |
| **7. 数据质量** | 质量规则、监控、智能报警、质量报告、问题闭环 | 规则配置、智能报警、质量报告、问题整改 |
| **8. 数据安全** | 分类分级、脱敏、权限(RBAC/ABAC)、审计、敏感识别 | 40+安全措施、50+敏感模板、脱敏、审计 |
| **9. 数据资产与服务** | 资产目录、标签、API服务、数据推送、自助分析 | 资产盘点、数据API、限流、调用监控、BI接入 |
| **10. 智能(AI)能力** | Copilot、NL2SQL、智能排错、数据洞察、Agent | NL2SQL、智能代码生成、智能运维、数据洞察Agent |

## 三、具体缺失清单（按优先级）

### 🔴 P0 级缺失（不补则平台不完整，强烈建议）

**缺-1：数据集成模块（整个缺失）**
- 现状：无数据源接入能力，首批只支持 Hive（经元数据/Spark）
- 建议：补 `数据源管理 + 离线同步任务`（MVP 至少支持 MySQL/Hive/文件），含字段映射、同步监控
- 依据：数据集成是数仓"原料入口"，标杆均有此模块

**缺-2：数据安全与权限（严重不足）**
- 现状：Spec 仅有 `sys_user` 角色 + 只读校验，无敏感数据保护
- 建议：补 `字段级脱敏 + 敏感字段识别 + 数据分类分级 + 审计日志`
- 依据：你调研的 qData/DataWorks 都把数据安全列为独立核心域；数仓涉及用户手机号等敏感字段，是合规红线

**缺-3：数据资产目录与检索（整个缺失）**
- 现状：有表/字段检索（F1.2），但无"资产"概念（标签、业务价值、生命周期、收藏）
- 建议：补 `资产目录 + 标签体系 + 资产详情(含质量/血缘/owner聚合) + 资产收藏`
- 依据：资产化是数据中台的核心价值主张

**缺-4：任务调度运维闭环（不完整）**
- 现状：F6 仅 Spark 自带调度 + 执行日志，无 DAG 编排、补数、重跑、监控告警
- 建议：MVP 先补 `补数据 + 重跑 + 失败告警(平台内通知)`，DAG 编排可后置
- 依据：没有补数/重跑/告警的调度对生产不可用

### 🟡 P1 级缺失（重要，可分期）

**缺-5：数据开发环境（WebIDE/工作流）**
- 现状：无在线 SQL 编辑器、无任务发布上线流程
- 建议：补 `SQL 编辑器(可复用 F3) + 脚本保存 + 调试 + 发布`，工作流 DAG 列为迭代2
- 依据：你现在所有 SQL 能力是"助手式"的，缺一个"安身之所"（编辑器+任务管理）

**缺-6：数据标准模块（独立缺失）**
- 现状：F2 的建模规范校验是"规则"，但无"数据标准/数据字典/术语表/落标映射"
- 建议：补 `数据标准定义 + 字段标准落标 + 数据字典 + 术语表`（术语表可与知识库 kb_alias 打通）
- 依据：标准是口径统一的前提，与你的 NL2SQL/知识库强相关

**缺-7：数据生命周期管理**
- 现状：无
- 建议：补 `数据保留策略 + 归档 + 过期清理（可结合数仓规范）`
- 依据：你记忆中有"正式库保留3年/归档表 archive_"规范，应平台化

**缺-8：自助分析与报表（模板）**
- 现状：F5 只有 NL2SQL/问答，无结果可视化
- 建议：补 `SQL 结果可视化(图表) + 基础报表/看板（轻量）`
- 依据：分析师用户需要"查完能看到趋势"

### 🟢 P2 级（增强，长期）

**缺-9：API 数据服务**
- 现状：无将数据对外封装为 API 的能力
- 建议：`数据API服务 + 限流 + 调用监控`（试点期可后置）
- 依据：数据服务化是政企标配，但单团队试点紧迫性低

## 四、与现有文档的衔接建议

本次梳理的缺失**不需要推翻现有 F1-F6**，而是**新增/强化**，建议落地方式：

| 缺失项 | 落地方式 | 建议优先级 |
|--------|---------|-----------|
| 缺-1 数据集成 | 新增模块 `F7 数据集成` | P0 |
| 缺-2 数据安全 | 强化现有"权限"为 `F8 数据安全` | P0 |
| 缺-3 资产目录 | 新增模块 `F9 数据资产` | P0 |
| 缺-4 调度运维闭环 | 强化现有 `F6` 调度 | P0 |
| 缺-5 开发环境 | 新增模块 `F10 数据开发`，复用 F3 | P1 |
| 缺-6 数据标准 | 新增模块 `F11 数据标准` | P1 |
| 缺-7 生命周期 | 并入 `F1 元数据` 或 F9 资产 | P1 |
| 缺-8 自助分析 | 新增模块 `F12 数据分析`，复用 F5 | P1 |
| 缺-9 API服务 | 新增模块 `F13 数据服务` | P2 |

> 调整后项目模块从 **F1-F6 扩为 F1-F13**，更贴近市场完整体系。

## 五、调研结论（我的意见）

1. **项目强项在"智能"层**（NL2SQL、SQL优化、口径问答、知识库RAG）——这是与市面产品的差异化亮点，应保留并深化。
2. **最大短板在"治理闭环"层**：数据安全、资产目录、调度运维、数据标准这 4 块是市面平台的基本盘，本项目的缺失会让平台"重智能、轻治理"，不够完整。
3. **试点定位可以取舍**：不必一上来做满 10 域。建议 P0 补齐 4 项（集成/安全/资产/调度闭环），P1 补 4 项（开发环境/标准/生命周期/分析），P2 视资源补 API 服务。
4. **与知识库打通**：数据标准(术语表)、数据字典应与知识库 RAG（kb_alias/kb_document）共用一套术语来源，避免重复维护。
