# 智能数仓平台 · 学习路线

> 依据本仓库已实现的代码整理。目标：不仅会跑通，更能深刻理解每一层在做什么、为什么这么设计、以及它能教给你哪些通用工程思维。

## 整体视图

```
阶段一 前置        →  阶段二 数与接口   →  阶段三 懂数仓
(Python/SQL/Git)     (FastAPI+ORM)         (分层/元数据/血缘)
        ↓
阶段四 智能化(核心)  →  阶段五 工程化
(规则引擎+NL2SQL)      (质量/调度/检索/安全)
```

---

## 阶段一 · 前置：看懂"零件"

这套项目外表复杂，拆开全是基础件：

- **Python 包结构**：`app/` 下按 `services/`（业务逻辑）、`routers/`（接口）、`schemas/`（校验）、`db/`（数据访问）、`core/`（安全/异常）划分，这就是模块化。
- **SQL**：平台所有查询最终都是 SELECT；SQL 既是数据语言，也是被分析的对象（阶段三）。
- **Git**：本地分支 / 提交 / 远程推送（`git remote`、`git push -u origin main`）。

> **认知点**：无论何种语言，"项目" = 「目录结构 + 入口文件 + 配置 + 依赖清单」。读陌生项目先找 `main.py` 与 `requirements.txt`。

### 对应文件

- `backend/main.py`（入口）
- `backend/requirements.txt`（依赖列表）
- `backend/run_dev.ps1` / `run_dev.sh`（启动脚本）

## 阶段二 · 数与接口：后端骨架

这套系统的"外壳"，负责所有 HTTP 交互：

| 概念                   | 说明                             | 真实位置                           |
| -------------------- | ------------------------------ | ------------------------------ |
| FastAPI 路由           | 一个 URL → 一个函数                  | `backend/app/routers/*.py`     |
| 依赖注入 Dependency      | 由框架注入数据库会话等依赖                  | `backend/app/deps.py`          |
| ORM (SQLAlchemy 2.0) | 表↔类、行↔对象，不手写裸 SQL              | `backend/app/db/models/*.py`   |
| Pydantic v2 Schema   | 进出数据的"安检门"，校验失败即报错             | `backend/app/schemas/*.py`     |
| 统一响应                 | 所有接口返回 `{code, message, data}` | `backend/app/core/response.py` |

> **认知点**：HTTP 服务本质 = 「收请求 → 校验 → 处理 → 统一格式响应」。这正是统一返回格式的来源。

## 阶段三 · 懂数仓：数据思维

"数仓"二字的真意，也是最有价值的一段：

- **分层建模**：`dim`/`dwd`/`ads` 等，原始数据 → 明细 → 汇总，层层变"干净、好查"。
- **元数据** = 关于数据的数据。采集 DDL、记录表 / 字段 / 分区，让你"查字典"而不是"翻表"。
- **血缘 Lineage**：`dwd订单明细 → ads日汇总`，回答"这个指标是谁算出来的"，是数据治理的核心。
- **SQL 解析 (sqlglot)**：把 SQL 字符串解析成一棵树，从而自动提取表/字段、检测 `SELECT *`、识别分区。

> **认知点**：数据平台不是"存数据"，而是"把数据的来龙去脉管理起来"。

### 对应文件

- `backend/app/services/metadata_ingest.py`（元数据采集）
- `backend/app/services/lineage.py`（血缘）
- `backend/app/services/sql_parser.py`（SQL 解析/只读校验）

## 阶段四 · 智能化（核心 · 建议优先深挖）

把"人写 SQL"变成"机器帮人写对 SQL"：

- **只读校验**：先剥离注释，再用正则 + 语法确认没有 `INSERT/DELETE/DDL`，防止 AI 生成危险语句。
- **优化规则引擎**：每条规则 = `key + 等级 + 判断函数`，命中即给出诊断（"规则式 AI" 的典型写法）。
- **NL2SQL 编排**：中文问题 → 构建表结构 prompt → 调千问 → 解析 JSON → 只读校验 → 失败降级生成。

> **认知点**：最有启发的&#x662F;**"失败兜底/降级"**&#x8BBE;计——LLM 不可达时自动退到规则生成。生产项目不是炫技，而是"处处有退路"。

### 对应文件

- `backend/app/services/optimizer.py`（优化规则引擎）
- `backend/app/services/nl2sql.py`（NL2SQL 编排）
- `backend/app/services/llm_gateway.py`（LLM 网关）

---

## 阶段五 · 工程化：从能跑到能上线

理解"安全、稳定、可观测"：

- **质量规则**（波动 / 非空 …）→ 校验 → 失败自动生成告警通知。
- **Celery 异步任务**：耗时任务丢队列，不卡请求（dev 模式同步执行）。
- **ES 全文检索 + SQL 回退**：检索快但"脆"，不可用即回退（再次体现兜底思想）。
- **AES-GCM 加密 LLM Key + JWT**：密钥加密存储、接口认证，上线底线。

### 对应文件

- `backend/app/services/quality.py`（数据质量）
- `backend/app/tasks.py`（Celery 任务）
- `backend/app/services/search.py`（检索与回退）
- `backend/app/core/security.py`（加密 / JWT）

## 学习建议

1. **按"改-跑-看"闭环学**：每学一个概念，去对应文件改一行 → 重启 → 看 `/docs` 或前端变化，别只看不碰。
2. **聚焦阶段四**：它最训练抽象与健壮性思维，也最适合后续扩展（加新优化规则、优化 prompt）。
3. **切真环境加深认知**：拿到连接串后把 `backend/.env` 切到 MySQL/ES/千问，观察"开发直跑"与"真实环境"在质量/检索/NL2SQL 上的行为差异。

### 推荐深入路径

- 先跑通：`python -m uvicorn app.main:app --reload` → 打开 `http://127.0.0.1:8000/docs`
- 再改一处：给 `optimizer.py` 增加一条新优化规则，看诊断是否生效
- 后想清楚：为什么只读校验能防住写操作？为什么 ES 要回退？
